# Problem Existence Evidence: Cluster Instructions

- Read `CONTEXT.md` completely before changing this cluster.
- Treat the research unit as a specific actor, job, circumstance, obstacle, and
  consequence—not a feature request or product idea.
- Stop at evidence that a problem is real, repeated, and behaviorally
  consequential. Do not infer business quality, market size, pricing, or a
  build decision.
- Keep supplied specifications and API notes as planning context. They are not
  collected market evidence and must never appear as such in `PROFILE.md`.
- Prefer first-person stories, workarounds, active solution seeking, named
  solution failures, and concrete consequences over generic dissatisfaction or
  hypothetical wishes.
- Always report breadth and concentration with mention counts. Distinct authors,
  threads, communities, source families, time span, and burst indicators prevent
  one loud user or viral thread from masquerading as recurrence.
- Preserve source-native engagement fields. Do not create a universal
  engagement score or compare unlike reactions, votes, likes, and views.
- Never infer cross-platform identity, population prevalence, authenticity, or
  complete historical coverage. Keep unavailable values missing, never zero.
- Use search results for discovery and corroboration. Hydrate evidence from the
  original page or native API before treating it as a mention.
- Reddit collection requires approved API access and a fresh terms review. Keep
  the cluster useful without Reddit; do not train models on Reddit content.
- Keep raw records, collection metadata, limitations, and stable evidence IDs
  inspectable. Every factual `PROFILE.md` item must cite those IDs.
- Keep future cluster-specific collection, normalization, and annotation logic
  in `problem_existence.py`. Do not invent its public interface before the
  top-level runner contract exists.
- Maintain all nine `PROFILE.md` sections, even though problem-existence evidence
  is this cluster's primary research focus.
